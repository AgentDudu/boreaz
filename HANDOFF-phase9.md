### The format, exactly

A patch **is** a parameter file. Nothing else. `config/params.ini`, `--params FILE`, and a saved
patch are one format with one parser.

```
# boreaz patch format 1
# name: Bright Grand
# instrument: assets/instruments/grand/library.txt

master_gain_db = -6.5
transpose_semitones = -3
...63 keys, in the table's own order...
```

- The header is **comments on purpose**: the parser refuses unknown keys (a phase-7 decision, and
  the reason a typo cannot produce a silent patch), and a patch's name and instrument are not engine
  parameters. So `--params mypatch.txt` loads a patch with no new loading code.
- `read_patch_meta` reads only the leading block of `#` lines and **stops at the first non-comment
  line**. Do not put a `# name:` below the parameters; it will not be seen.
- Numbers are written by `std::to_chars` with no precision — the shortest text that reads back as the
  same float: `amp_sustain = 0.7`, not `0.699999999`. Whole-number rows print whole (`octave_shift =
  2`), because the reader rejects `1.5` **and** would reject `2.0`.
- Every parameter is written every time. Do not "optimise" this into a diff-against-defaults file: it
  would change meaning whenever a default changes, and `adopt_patch` layers one file on another.
- The whole body is built in memory and written in one `ofstream` go. A patch that stops half way
  loads and is wrong.

### The API (all in `boreaz/config/params_file.h`)

```cpp
bool load_params_file(path, Params&, error);                  // strict, all-or-nothing
bool set_param_from_text(flag, key, value, Params&, error);   // same parser, for CLI flags
std::string defaults_path();                                  // config/params.ini, walks up 3 levels
std::string patches_dir();                                    // the factory patches, same walk
std::string user_patches_dir();                               // %APPDATA%/Boreaz/patches, created
std::string known_keys();                                     // the 63 keys, for the error message
bool save_params_file(path, Params&, name, instrument, error);
bool read_patch_meta(path, name, instrument, error);
```

### The panel (`src/gui/params_panel.cpp`, block starts after the `Defaults` button)

`Patch`: a name field, `Save`, then **two folders** — `Factory patches` and `Your patches` — each
listed as one button per `.txt` (labelled from its own header; an unreadable file still gets a row
labelled by filename), and `Rescan`. Hover shows the file and the instrument the patch wants.

- **Save writes into the player's folder** (`user_patches_dir()`), never the repository's. The name
  is trimmed and rejected if it contains a dot, slash or colon — a name is text typed into a box, and
  `..` is a save outside the folder.
- **Load** = `adopt_patch`: parameters in through `engine.set_params` (the engine's ramp is what makes
  a patch change without a click), then the instrument through `request_instrument`, which is the same
  code the `Load` button uses.
- A patch naming **no** instrument keeps the library that is playing. A patch whose library is missing
  says why in the panel's line. Neither goes quietly to the synthesiser — phase 4's rule.
- The instrument switch itself still waits for silence (`carry_pending`), because adopting a library
  rebuilds the voice pool.

### The factory patches, and the two rules that came with them

`patches/` holds eight files, written by `tools/factory_patches.py`: one delta dictionary per patch,
expanded against `param_table.cpp` so a default lives in exactly one place. `--verify` prints nothing
while they agree and lists the differences when a hand edit makes them disagree; `--write` rewrites
them from the recipe.

- **A patch is complete or it is not a patch.** Every file carries all 63 keys, because `adopt_patch`
  layers a file onto whatever is already playing: a key left out is not "unchanged", it is "whatever
  the last patch left". The cost of the rule is that adding a parameter row means regenerating the
  patch set — the test fails until you do, on purpose.
- **A factory patch names no instrument.** A library path is a path on one machine; nothing
  machine-local is in git, and an empty instrument is the loader's own rule for "keep what is playing".
- **Saves go to `%APPDATA%/Boreaz/patches`.** The repository's `patches/` is read by the app and never
  written to; a test asserts no factory file sits in the folder the app writes to. Before this, a save
  typed "Bass" overwrote the shipped voice of that name.

Measured by render (four fixtures, best of 3 — the numbers are in PLAN's phase-9 row and
`docs/pr-factory-patches.md`). The short version: **no patch reaches the ceiling** — the loudest patch
on the heaviest fixture is `piano-fortissimo` at peak **0.511** (16 voices), where the shipped
`config/params.ini` on the same fixture is 0.869 — and the dynamics presets measure the master gain
they name (**0.144 / 0.282 / 0.511** = -6 / 0 / +6 dB). CPU on that fixture is **1.01-1.08 %** of one
core for the registers and **0.54-0.55 %** for the piano presets, inside the 8 % row; the sampled side
is higher only because of the room (+0.10 points on four voices, +0.21 on sixteen).

### Decisions already made — do not re-litigate silently

- **A bad key refuses the file whole**, prints the reason in the panel, and the sound that was playing
  keeps playing. Decided 2026-11-04, **reversing** PLAN's row-9 wording ("loads with warning and keeps
  sane defaults"), which PLAN now records as reversed. Reason: the parser has always taken a file as a
  unit or not at all, and a half-loaded preset is some of one sound and some of another — a sound
  nobody wrote and nobody can name.
- **The browser is a directory listing.** No preset database, no index, no file dialogs.
- **The room's shipped number is 0.35 / 0.30 / 0.18** on the three dynamics presets (pp / mf / ff),
  and 0 on the registers. Softer playing gets the bigger room. This closes §6's "should a dry grand
  have reverb by default?" and honours phase 8's "the room arrives with a preset". Written into §7.
- **The shipped patches folder is read-only to the app**; the player's own folder is
  `%APPDATA%/Boreaz/patches`. Written into §7.
- `env2_*` is gone: the modulation envelope is `mod_env_*` in the file, the panel, the enum
  (`ModSource::kModEnv`) and the voice. The amp envelope keeps its bare `amp_*` names.

## What is left, in the order to take it

1. **App config file** — audio device, MIDI device, last patch, instrument path. Deliberately **not**
   `params.ini` (that is parameters; this is the machine's setup) and deliberately the same
   `key = value` shape if it can be, but its keys are not engine parameters, so do not feed it to the
   strict engine parser without a separate table or a separate reader. `user_patches_dir()` is the
   pattern for finding the per-user directory on Windows and off it.
2. **Autosave on exit** — pairs with (1). Decide what "autosave" means for a patch: overwrite the last
   patch, or a session file that `--gui` re-loads. PLAN says autosave on exit; it does not say where.
   Do not make it overwrite a factory file — saves only go to the player's folder now.
3. **The hole in the exit criterion.** It demands the round trip cover `voice-kind`, and **no such
   parameter exists** (`voice_kind`: 0 hits in the tree — the voice kind is implied by whether a
   library is loaded). Ask the operator: add a `voice_kind` row to the table, or accept that
   `instrument` already carries it and mark the criterion met. Do not invent a parameter for it
   without asking.
4. **The shipped master default, noticed and not acted on.** `master_gain_db = -4` with
   `fx_limiter_threshold_db = -4`: a unison saw held across all 16 voices peaks at **-3.35 dBFS**,
   8 dB above the limiter's threshold. No factory patch is near that (the loudest is 0.511). Worth an
   operator decision about the limiter ceiling, not a change in a patch PR.

## Verified vs not — do not overclaim

- **Proven:** the round trip — each of the 63 rows at minimum, maximum and default comes back
  bit-exact (`==`, not `Approx`), and save→load→save gives identical bytes at all 190 cases. A refused
  file leaves the `Params` it was given untouched. The factory patches load through the same strict
  reader, and every one of them takes all 63 rows to a legal value. Levels and CPU of every patch are
  measured, not guessed. Both render-contract gates pass, goldens unmoved.
- **Not proven:** the panel's click path. Both cases in `tests/test_params_panel.cpp` call `toggle()`,
  so the Patch block, both folder scans and the buttons **execute** under the suite, but **no button is
  pressed** — there is no click harness. The new folder headers have never been looked at in a window
  either, in a 340 px column or anywhere else.
- Nobody has listened to the eight patches. The numbers say they are clean and do not clip; whether
  `upper` is a good sound is an ear, not a peak.

## Gotchas

- **Adding a parameter row breaks `tests/test_factory_patches.cpp` on purpose.** Fix by
  `python tools/factory_patches.py --write`, then **re-render the patched set** and re-check the
  numbers — a new parameter is a new way to be loud.
- **Never read a patch value off a `Params` field's C++ type.** `mod_env_sustain` is a signed old
  depth (-1..1) in the struct while the table and `mod_env_pos` treat it as a 0..1 level; the
  generator's own comment says the sign convention is not encoded. Use the table's min/max — that is
  what the generator does, and what caught a `bass.txt` that asked for -0.35.
- `patches_dir()` walks `"", "./", "../", "../../", "../../../"`. Running the app from `build/` means
  the factory folder is `../patches` — the repository's. From a release directory it is `./patches`,
  which is why the release zip carries `patches/` next to the exe (`tools/make_release_zip.py`).
- The parser is strict in two directions: the whole string must be a number, and the number must be
  inside that parameter's own range. `Params::clamp_all` is **not** a safety net for a bad file.
- `param_read` / `param_write` / `param_is_integer` are how you touch a parameter generically. The
  eight cables live inside `std::array` members and set neither `real` nor `integer`, so **never guess
  how to reach a parameter** — go through the table. That bug class already bit the reader once, and
  the patch generator reads the same functions.
- clang-format is enforced **only on changed files**, so untouched files carry drift and will be
  reformatted the moment you touch them. Put that in the commit message when it happens.
- PLAN's phase rows are **single long table lines**. Edit them with a script that splits on the line
  prefix and asserts the row ends in ` |`; a stray `|` corrupts the table.
- PR bodies live in `docs/pr-<topic>.md` and are committed with the PR. Commit messages are narrative
  ("what it fixes, what was wrong, what is proven, what is not done") — see `git log`.
- pi-lens flags `src/tools/render/main.cpp` with phantom parse errors ("expected unqualified-id").
  They are C-grammar parse artifacts: an active LSP probe returns **confirmed clean** and the compiler
  builds the TU with zero errors. Do not restructure valid C++ to satisfy them.
